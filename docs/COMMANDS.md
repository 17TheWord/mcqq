# 三个面与命令执行

QQ 侧支持三种会话：**群**、**频道的文字子频道**、**私聊**。三者的桥接逻辑共用一套，
只有"键从哪来"和"怎么发"分叉。

这份文档讲三件事：**三个面各自的字段与限额**、**权限模型**、**命令执行这条路**。

## 一、三个面

| 面 | 会话标识 | 身份字段 | 发消息 |
| --- | --- | --- | --- |
| 群 | `group_openid` | `author.member_role`（`member` / `admin` / `owner`） | `api().group()` |
| 子频道 | `channel_id`（配置里另写 `guild-id`） | `member.roles`（身份组 ID 列表） | `api().channelMessages()` |
| 私聊 | `user_openid` | 没有 | `api().c2c()` |

**身份随事件来**，不用额外调接口 —— 所以权限判断是纯函数，离线可测。
（另一条路 `GET /v2/groups/{gid}/members/{mid}` 也能拿 `member_role`，但那个接口文档写着
「内邀接入中，仅白名单机器人可用」，所以**不要依赖它**。）

会话标识与"该取哪个键"交给 SDK 的 `ReplyTarget`（`scene()` / `targetId()`）——
那张表 SDK 里已经有了，不必自己记一份。见 `QqEvents`。

### 频道的身份组 ID

官方文档「频道身份组对象(Role)」里的内置值：

| ID | 描述 |
| --- | --- |
| 1 | 全体成员 |
| 2 | 管理员 |
| 4 | 群主/创建者 |
| 5 | 子频道管理员 |

其余都是**自定义身份组**（文档里没有"超管"这个内置项）。所以判断不能写死这几个 ——
配置里有一份可填的 ID 列表。

### 消息限额（决定"回显怎么发"）

| 场景 | 被动回复有效期 | **每条消息可回复次数** |
| --- | --- | --- |
| 单聊 | 60 分钟 | **4 次** |
| 群聊 | 5 分钟 | 5 次 |

主动消息另有额度（单聊 1000 条/用户/天、群聊 1000 条/群/天），而且**用户可以在客户端关掉
「允许主动发送」**，关掉后主动消息一律失败 —— 所以它不能当可靠通道用。

## 二、权限模型

放行有三个**互相独立**的来源，任一命中即可：

1. **白名单** —— QQ 侧的 openid，不看身份；
2. **额外身份组**（只对子频道有意义）—— 子频道管理员（`5`）与自定义身份组 ID；
3. **内置层级** —— `allow: none / owner / admin`。

写成判断就是（`CommandAccess.permits`）：

```
群：   白名单 || allow 覆盖(member_role)
频道： 白名单 || 额外身份组命中 || allow 覆盖(roles ∩ {2, 4})
私聊： 白名单        // 没有身份概念
```

`allow` 的语义（**包含关系向上**，管理员能做的群主也能做）：

| `allow` | 群（`member_role`） | 频道（`roles`） |
| --- | --- | --- |
| `none` | 都不行，只认白名单与额外身份组 | 同左 |
| `owner` | `owner` | 含 `4` |
| `admin` | `owner` 或 `admin` | 含 `2` 或 `4` |

**内置的 `2` / `4` 归 `allow` 管，`roles` 只放额外的**（子频道管理员与自定义）。
`roles` 里写了 `2`/`4` 会被剔掉并在 `/qq status` 的 problems 里提示 —— 免得有人以为
"没写 2 所以管理员用不了"。

**私聊没有 `allow`**：C2C 事件里没有角色字段，写了会被忽略并提示。

## 三、命令执行

```
入站消息
  ├─ 不以 command.prefix 开头 → 按普通消息处理（群/频道转发进聊天栏；私聊忽略）
  └─ 以 prefix 开头（三个面都一样）
       ↓
   权限判断 ── 不通过 → 群 / 子频道：回一句"你没有权限"
                     私聊：**静默**（不向陌生人确认这个机器人在这儿）
       ↓ 通过
   ① 走 RCON 跑命令
   ② 把回显聚合成**一条**回复
   ③ event.reply(...)
```

**总开关 `command.enabled` 默认关** —— 这是唯一一条"从 QQ 能影响服务器"的路径。

### ⚠️ 群里必须 @ 机器人（否则只能用主动消息回）

官方文档对 `msg_id` 的说明是：**「被动回复的消息 ID，从 `GROUP_AT_MESSAGE_CREATE` 等事件的 `d.id`
获取，5 分钟内有效」** —— 而 `GROUP_AT_MESSAGE_CREATE` 就是"@ 了机器人"那个事件。

所以：

* **@ 机器人执行命令** → 走被动回复 ✓（不占额度、用户关不掉）；
* **全量模式下收到的普通消息**（没 @）→ 它的 id 不能当 `msg_id` 用 ✗，平台会回
  `40034024 请求参数 msg_id 无效或越权`。这时改用**主动消息**兜底 —— 代价是占主动消息额度
  （1000 条/群/天），而且**用户可以在客户端关掉「允许主动发送」**，关了就真的发不出去。

这条兜底写在 `McCommands.reply` 里：先试被动回复，被拒且是"这条路走不通"那几种错误码
（`40034024` / `40034005` / `304103` / `40034128`）就改走主动消息，并在日志里说明。

### 实测：全量模式下被动回复**同样可用**

一开始真机上 @ 着机器人发命令，回显却是走主动消息发出去的：

```
执行命令（MC）：list
被动回复走不通（err_code=40034024），改用主动消息发回显
```

当时看起来像"全量模式不给被动回复"，其实是 **SDK 的 bug** —— 它拿信封的 id 当 `msg_id` 发，
而平台要的是消息自己的 id（`d.id`）。真机上两个 id 长这样：

```
信封 id = GROUP_MESSAGE_CREATE:0d2kqbozuelnudywrcy5va9w...
d.id    = ROBOT1.0_0D2KqBozUelnUDywrCY5vdjxMd5x...
```

修掉之后（SDK 改成读 `d.id`），**同样一条 `@机器人 /mcc list`，被动回复直接成功**，
日志里不再出现那句兜底 —— 不占主动消息额度了。

所以：**全量模式和被动回复并不冲突**，两个功能可以同时要。兜底仍然留着（被动回复有
5 分钟 / 5 次的限制，超了就得靠它）。

## 四、运维能看到什么

* `/qq status` 始终报"命令执行：开着 / 关着"，以及每个目标与私聊各自是谁能用；
  `command.enabled` 开着但没有任何目标配 `command` 时，会当场记一条问题。
* `/qq run <命令>` 走的是**和 QQ 侧同一个方法**，所以运维不用真去 QQ 发一条就能确认这条路通不通。
* 配置里的 `debug: true` 会把每条消息的身份（openid / `member_role` / `roles`）和每一次丢弃的原因
  打进服务端日志（前缀 `[debug]`）。
